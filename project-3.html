Muti-Process Web Crawler

A multiprocess application that was created in C that deals with the producer-consumer problem via semaphores, mutexs, and atomic variables to avoid deadlocks and run efficiently.

Project Overview

This project is a multiprocess webcrawler written in C, designed to recursively search web pages by parsing their content for additional URLs and PNGs. Focussing on advanced systems programming concepts, including interprocess communication, concurrency, and data structure design. The purpose of this webcrawler was to find PNGs in the relevant links and store all of them until reaching either a set depth limit, or until finding the desired number of PNGs.

Frontier Management with a Stack: A dynamically allocated stack is used to manage the frontier of URLs to visit. This ensures a Last-In-First-Out (LIFO) order, allowing depth-first crawling of web pages. 


    typedef struct frontier_stack{
        int size;
        int pos;
        char **urls;
    } STACK;
    
    int stack_init(STACK *stack, int starting_size){
      stack->urls = malloc(starting_size * sizeof(char *));
      stack->pos = -1;
      stack->size = starting_size;
      return 0;

Synchronization: Synchronization is a key concern in multiprocess applications and this project was no different. Semaphores, mutexes, and atomic ints were used extensively to ensure that all processes were able to do their work and exit safely, avoiding any potential deadlocks. An example below shows the `thread_todo` function, which is the task for all web crawling threads. 

                      
    void *thread_todo(void *arg){
        bool waiting_appended = false;
        while(atomic_load(&png_counter) < m){
            if(atomic_load(&threads_waiting) >= t){
                pthread_mutex_lock(&frontier_mutex);
                if(frontiers.pos == -1){
                    pthread_mutex_unlock(&frontier_mutex);
                    break;
                }
                pthread_mutex_unlock(&frontier_mutex);
            }
            thread_crawl(&waiting_appended);
        }
    }

It continuously runs as long as fewer than `m` tasks have been processed, checking if other threads are waiting to avoid overloading the system (via `threads_waiting`). The function uses `frontier_mutex` to safely access and check the `frontiers` queue, which holds URLs to be crawled, and it ensures no thread proceeds when the queue is empty. If the queue has no URLs, the thread exits. The `waiting_appended` flag tracks if the thread is in a waiting state for synchronization with others. The atomic variables like `threads_waiting` and `png_counter` are used to manage synchronization between threads and ensure no thread starts crawling if too many are waiting or if the overall task limit `m` (the number of processed PNGs) is reached.

The combination of mutex locks and atomic operations ensures thread safety and coordinated task processing without race conditions or resource contention.
